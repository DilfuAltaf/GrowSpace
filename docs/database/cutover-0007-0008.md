## 1. What these migrations do

| Migration | Change | Reversible inside its own transaction |
| :--- | :--- | :--- |
| `0007_create_care_schedules.sql` | Creates `care_schedules`; adds nullable `care_tasks.schedule_id` + FK (`ON DELETE SET NULL`) + partial index; rewrites `care_tasks_task_type_check` to allow `pruning` | Yes — DDL is transactional in PostgreSQL |
| `0008_create_assistant_conversations.sql` | Creates `assistant_conversations` and `assistant_messages` with FKs, checks, and indexes | Yes — DDL is transactional in PostgreSQL |

Ordering is mandatory: `0007` depends on `users`, `gardens`, `plants`, `care_tasks` (all from
`0001`–`0004`); `0008` depends on `users`, `gardens`, `plants`. The runner refuses out-of-order
or duplicate versions.

Both files are additive. `0007` briefly takes an `ACCESS EXCLUSIVE` lock on `care_tasks` while it
adds a column, an FK, an index, and swaps a check constraint. Plan a low-traffic window.

`0007` was authored after `0006`, so its audited checksum in `scripts/lib/migration-runner.mjs` is
`b1c672f5d04828fd3f958ac13546799ce5fbda12d4e6cece23b3548a3526aa63`, and `0008`'s is

## 2. Transaction, locking, and validation behavior of the runner

`scripts/run-migration.mjs` + `scripts/lib/migration-runner.mjs` provide:

1. **Session advisory lock** (`pg_try_advisory_lock(73928194)`) — a second runner aborts instead of
   racing the first.
2. **Per-file transaction** — `BEGIN` → `pg_advisory_xact_lock` → migration SQL → insert into
   `_schema_migrations` → `COMMIT`; any error triggers `ROLLBACK` and a non-zero exit.
3. **Drift detection** — a modified or missing already-applied migration halts the run.
4. **Monotonic ordering** — pending versions below the highest applied version halt the run.
5. **Postflight catalog parity** — table inventory, primary keys, composite/column-specific FKs,
   security check expressions, partial indexes, and connection counts. It exits non-zero on any
   mismatch, so a silent half-applied schema cannot be mistaken for success.

Recovery layers, in order of preference:

| Layer | Mechanism | Blast radius |
| :--- | :--- | :--- |
| 1 | Automatic `ROLLBACK` of the failing migration file | That file only; earlier files stay committed |
| 2 | Pre-cutover Neon snapshot branch | Whole database, copy-on-write, seconds to create |
| 3 | Neon point-in-time restore within the project's retention window | Whole database, to any timestamp in the window |
| 4 | Forward fix with a new migration file | Never edit an applied migration |

A restored branch has its own endpoint. Repointing traffic requires either
`neon endpoints update <endpoint-id> --branch <restored-branch>` or updating `DATABASE_URL` and
restarting the API. Restoring a branch alone does not redirect the running application.

## 8. Post-migration smoke tests

Use a disposable account, not a real customer account. All mutating calls need `Origin` and, once
authenticated, `X-CSRF-Token` from `GET /api/auth/session`.

```bash
export API="https://<api-host>"
export WEB="https://<app-host>"
```

### 8.1 Recurring care schedules

```bash
# Create a schedule; response 201 with { schedule, initialTask }
curl -sS -c cookies.txt -b cookies.txt \
  -H "Origin: $WEB" -H 'Content-Type: application/json' \
  -d '{"gardenId":"<garden-uuid>","title":"Water tomatoes","taskType":"watering","intervalValue":3,"intervalUnit":"days","priority":"normal"}' \
  "$API/api/tasks/schedules"
```

Checks:

- `schedule.id` exists and `initialTask.scheduleId === schedule.id`.
- `GET /api/tasks/schedules?isActive=true` includes the new schedule with `nextDueAt` populated.
- `PATCH /api/tasks/schedules/<id>` with `{"intervalValue":5,"intervalUnit":"days"}` returns 200.
- `PATCH /api/tasks/<initialTask.id>` with `{"status":"completed"}` returns 200 and generates exactly
  one new pending task for the schedule; `nextDueAt` advances by one interval from completion time.
- Completing the same task again must not create a second pending task (deduplication).
- `DELETE /api/tasks/schedules/<id>` returns 204. The historical task still exists and its
  `scheduleId` is `null`; `care_tasks.status`/`completedAt` are unchanged.

SQL cross-check (substitute the schedule UUID):

```sql
SELECT id, status, due_at, completed_at, schedule_id
FROM care_tasks WHERE schedule_id = '<schedule-uuid>' OR id = '<task-uuid>';
```

Expected: at most one `pending` task for the schedule after completion, and no task lost on
schedule deletion.

### 8.2 AI assistant conversation persistence

AI credentials are optional. With `GROQ_API_KEY` unset, the endpoint must still answer from the
deterministic fallback and persist the exchange.

```bash
# Send a message in a new thread (200)
curl -sS -c cookies.txt -b cookies.txt \
  -H "Origin: $WEB" -H "Content-Type: application/json" \
  -H "X-CSRF-Token: <csrf-token>" \
  -d '{"message":"Which of my plants need attention today?"}' \
  "$API/api/assistant/chat"

# List threads (200, contains the new conversation)
curl -sS -b cookies.txt "$API/api/assistant/conversations"

# Read the thread (200, two messages: user then assistant)
curl -sS -b cookies.txt "$API/api/assistant/conversations/<conversation-id>"

# Delete the thread (204), then confirm 404
curl -sS -b cookies.txt -X DELETE -H "Origin: $WEB" -H "X-CSRF-Token: <csrf-token>" \
  -w '%{http_code}\n' -o /dev/null \
  "$API/api/assistant/conversations/<conversation-id>"
```

SQL cross-check:

```sql
SELECT c.id, c.user_id, count(m.id) AS messages
FROM assistant_conversations c
LEFT JOIN assistant_messages m ON m.conversation_id = c.id
WHERE c.id = '<conversation-id>'
GROUP BY c.id;
```

Expected: conversation owned by the test user with two messages before deletion; zero rows after.
Deleting a garden or plant must set `garden_id` / `plant_id` to `NULL` on the conversation, not
delete it.

If a step fails after migrations were applied, the schema is still additive: keep traffic on the
previous deploy, capture the failing request/response, and use the recovery layers in section 2.
Do not re-run applied migrations and do not manually `INSERT` fabricated rows into
`_schema_migrations`.
